Evidence Identity v1
====================

Purpose
-------
Evidence Identity v1 gives each normalized event record a durable forensic
locator, stored as `events.evidence_record_key`. The key represents the
underlying evidence record within a case, not the parser version, processing
path, enrichment state, analyst state, or current application workflow state
that produced a normalized row.

Selector key distinction
------------------------
`selector_key` remains the operational hunting UI and mutable event-state
selector. It intentionally keeps the current record-or-second fallback behavior.

`evidence_record_key` is the forensic evidence identity. Consumers that need
authoritative record provenance must use it with mandatory case scope.

Identity algorithm
------------------
The v1 algorithm is generated during normalized parser ingestion and is stored
with `evidence_identity_version = "1"`. It uses SHA-256 over canonical JSON with
deterministic field ordering and the algorithm version. The descriptive quality
label is not hashed.

Identity includes:
- case scope: `case_id`;
- stable evidence-source scope: `case_file_id` when present, otherwise a
  declared stable source evidence identifier, otherwise source filename/host and
  artifact type;
- explicit native/source-record ID when trustworthy;
- canonical retained raw source record when available;
- stable normalized source fields only when no retained raw source record exists;
- timestamp at ClickHouse retained identity precision, milliseconds, when the
  timestamp participates in fingerprint identity.

Identity explicitly excludes:
- parser version;
- physical processing path when stable source evidence identity exists;
- search blob;
- analyst tags and analyst notes;
- IOC state;
- noise state;
- MITRE, Sigma, or Hayabusa enrichment;
- AI/model output;
- parser provenance annotations;
- processing/index timestamps;
- graph fields and future edge state;
- detection scores and mutable enrichment confidence.

Identity hierarchy
------------------
Native:
  Used only when the producer explicitly declares `record_id` to be a genuine
  source-native record identifier, or for retained EVTX rows where the parser
  family is known to carry Windows Event Log `EventRecordId` / `RecordNumber`.
  The native ID is scoped to the case and source evidence.

Source identifier:
  Used when parser metadata carries a recognized stable source-record identifier
  such as `source_native_id`, `source_record_id`, `row_id`, `sqlite_rowid`,
  `entry_id`, or `uid`. Numeric zero is valid and is serialized as `0`.

Fingerprint:
  Used when no stronger identifier exists. Canonical retained `raw_json` is
  preferred. If raw source data is unavailable, v1 falls back to an allowlist of
  stable normalized source fields. Arbitrary `extra_fields` are not hashed.

Legacy fallback:
  Used for retained rows that lack native IDs, source identifiers, retained raw
  records, and stable normalized source fields. The quality label documents the
  weakness of the retained material, but does not change the key digest.

Native ID opt-in contract
-------------------------
Parsers and event producers must not rely on a positive `record_id` alone. A
producer opts in by setting `ParsedEvent.native_record_id_authoritative = True`.
During ClickHouse insertion this is also retained in `extra_fields` as
`native_record_id_authoritative: true` and `record_identity_kind: native`, so
future backfills can reconstruct the same identity.

Current reviewed opt-ins:
- EVTX parser: Windows Event Log `EventRecordId` / `RecordNumber`.

Current reviewed non-opt-ins:
- CyLR acquisition summary: `record_id` is the extracted-file count and is not a
  source-native record identifier.
- Generic parser row numbers/counters remain non-native unless separately
  reviewed and explicitly marked later.

Locator metadata
----------------
`EvidenceRecordLocator` intentionally remains metadata-rich. It may include case
ID, evidence key, source type/table, selector key, source file, current source
path, CaseFile ID, host, artifact type, timestamp, event ID, record ID, parser
version, and explicit source-native identifier.

Some locator fields are intentionally not part of the permanent evidence hash.
Parser version and current source path are useful provenance/display metadata,
but they must not rename the underlying evidence record.

Lookup behavior
---------------
`get_event_by_evidence_record_key(case_id, evidence_record_key)` requires case
scope. Empty keys return no event without querying. Cross-case resolution is not
possible because the query always constrains `case_id`. Selector lookup is
unchanged.

Migration and production backfill
---------------------------------
The Evidence Identity migration adds missing identity columns, ensures
`idx_evidence_record_key` exists on upgraded `events` tables, verifies/recreates
`events_buffer` when its insertable schema differs from `events`, and backfills
identity values with a shadow-table rewrite.

The backfill does not issue one synchronous `ALTER TABLE ... UPDATE` per event.
It:
- creates `events_evidence_identity_backfill` from the current `events` schema;
- streams source rows with `query_rows_stream`;
- computes missing identities, or recomputes existing identities when
  `--recompute-existing` is supplied;
- inserts rows into the shadow table in bounded batches;
- validates shadow row count against the original table;
- drops and recreates `events_buffer`;
- atomically renames `events` to `events_evidence_identity_previous` and the
  shadow table to `events`;
- materializes the evidence-key index when requested by the migration flow.

Restart and rollback behavior
-----------------------------
The migration is idempotent. If interrupted before swap, rerunning drops the
interrupted shadow table and starts a fresh shadow copy. If validation fails
before swap, the original `events` table remains untouched and the shadow table
is dropped. After a successful swap, the previous table remains as
`events_evidence_identity_previous` until operators choose to remove it after
validation. Rollback is to stop services and rename that previous table back to
`events`, then recreate `events_buffer`.

Operational complexity
----------------------
The rewrite is O(number_of_events) row streaming and batched inserts, with a
bounded number of ClickHouse DDL operations. It is not O(number_of_events)
ClickHouse mutations. Batch size controls Python memory and insert size.

Release update instructions
---------------------------
Run this migration as an explicit maintenance operation. Do not hide a large
ClickHouse rewrite behind normal application startup.

Recommended operator flow:

1. Stop CaseScope services:
   `sudo -n /usr/bin/systemctl stop casescope-web`
   `sudo -n /usr/bin/systemctl stop casescope-workers`
   In the standard repository deployment, scheduled Celery work is managed with
   the worker service. If an installation has a separate beat unit, stop that
   exact unit before continuing.

2. Back up ClickHouse before rewriting events.

3. Run the normal event schema migration:
   `cd /opt/casescope`
   `python3 migrations/add_events_table.py`

4. Check Evidence Identity migration status:
   `python3 migrations/add_evidence_record_identity.py --status`

5. Dry-run the Evidence Identity migration:
   `python3 migrations/add_evidence_record_identity.py --dry-run`

6. Backfill missing identities:
   `python3 migrations/add_evidence_record_identity.py --batch-size 10000`

7. For deployments that already ingested Phase 0A rows under 4.12.5 and need
   those keys repaired, explicitly recompute existing keys:
   `python3 migrations/add_evidence_record_identity.py --batch-size 10000 --recompute-existing`

8. Validate after the rewrite:
   `python3 migrations/add_evidence_record_identity.py --status`
   Confirm row counts match expectations and empty-key count is zero or
   explainable for retained rows without reconstructable source material.

9. Restart services after validation:
   `sudo -n /usr/bin/systemctl start casescope-workers`
   `sudo -n /usr/bin/systemctl start casescope-web`
   If an installation has a separate beat unit, start that exact unit after the
   worker service.

Expected maintenance impact
---------------------------
The backfill reads and rewrites the full `events` table unless scoped. Large
cases should be scheduled during a maintenance window. CPU cost comes from
canonical JSON hashing in Python; ClickHouse cost comes from streaming reads,
batched inserts, index materialization, and table rename operations. Existing
analyst, IOC, noise, MITRE, selector, and mutable event-state columns are copied
unchanged.

Future graph guidance
---------------------
Graph edges should store provenance as case ID plus `evidence_record_key`, with
optional locator context such as source table, source file/path, case file ID,
source host, artifact type, timestamp, event ID, record ID, parser version, and
source-native identifier. Do not use `selector_key` as the permanent graph-edge
evidence identity.
