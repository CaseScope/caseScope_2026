Evidence Identity v2
====================

Why v2 exists
-------------
Phase 0A v1 was introduced before final architecture acceptance and included
some interpretation-dependent hash inputs. v2 locks the forensic identity
contract before durable graph provenance depends on these keys. New keys are
stored as `erk:v2:<sha256>` with `evidence_identity_version = "2"`.

Purpose
-------
Evidence Identity v2 identifies the underlying forensic source record within a
case and stable evidence source. It does not identify today's parser
interpretation, enrichment, analyst state, model output, processing path, or
application workflow state.

`selector_key` remains separate. It continues to support existing hunting UI and
mutable event-state behavior and is not replaced by this work.

Identity algorithm
------------------
The key is SHA-256 over canonical JSON with deterministic dictionary ordering,
the algorithm name, and `version = "2"`. The descriptive quality label is not
hashed.

Hierarchy:

1. Native identity:
   `algorithm/version + case_scope + source_scope + native identity type + native record ID`

   Current reviewed native opt-in:
   - EVTX: `evtx_record_id`, sourced from Windows Event Log `EventRecordId` /
     EvtxECmd `EventRecordId` or `RecordNumber`.

2. Stable source identifier:
   `algorithm/version + case_scope + source_scope + explicit source-record identifier type/value`

   Recognized metadata names alone are not authoritative. A parser or producer
   must explicitly opt in with:
   - `source_record_identifier_authoritative = true`
   - `source_record_identifier_type = "<stable source-scoped semantic type>"`
   - `source_record_identifier_value = "<stable source-scoped value>"`

   Discovered metadata such as `source_native_id`, `source_record_id`, `row_id`,
   `sqlite_rowid`, `entry_id`, and `uid` may be exposed in locators/details, but
   they do not outrank raw source evidence unless the explicit authority
   contract above is present. Numeric zero is valid when explicitly authorized.

3. Raw-backed fingerprint:
   `algorithm/version + case_scope + source_scope + canonical retained raw source record`

   Raw source keys and values are preserved. A raw field named `model_name`,
   `ioc_types`, or any other CaseScope-like metadata name is still part of the
   original forensic record and remains hash material.

4. Normalized fallback:
   Used only when no native ID, source identifier, or usable retained raw source
   payload exists. It uses a conservative allowlist of stable source-derived
   normalized fields, with timestamps serialized at ClickHouse-retained
   millisecond precision.

5. Legacy fallback:
   Used for retained rows without reconstructable source identity material. The
   quality label documents weakness only and does not affect the digest.

Source scope
------------
When `case_file_id` exists, it is the primary within-case evidence-source
anchor. Physical `source_path` and parser version are not hash material. Without
a CaseFile anchor, v2 uses the strongest retained stable source-evidence
identifier, falling back to source filename/host/artifact/path only when no
stronger scope exists.

What v2 does not hash
---------------------
v2 excludes parser version, physical processing path when stable source scope is
available, search blob, analyst tags/notes, noise state, IOC state,
MITRE/Sigma/Hayabusa enrichment, AI/model state, parser provenance annotations,
indexing timestamps, selector keys, and future graph state.

Raw versus normalized behavior
------------------------------
When retained `raw_json` contains a usable source payload, parser-derived fields
such as `source_host`, `event_id`, normalized timestamps, source timezone, and
parser version do not participate in the fingerprint. If the raw source record
changes, the key changes. If CaseScope enrichment outside raw source data
changes, the key does not change.

Raw canonicalization is separate from normalized fallback cleanup. Raw JSON
preserves source keys and source values including JSON null, false, zero, empty
strings, empty arrays, and empty objects. Original list order is preserved.
Deterministic serialization only sorts dictionary keys and normalizes supported
non-JSON scalar objects, such as datetime/date and Decimal, if they appear before
JSON conversion. These raw payloads remain distinct:
- `{}`
- `{"a": null}`
- `{"a": ""}`
- `{"a": 0}`
- `{"a": false}`

Migration behavior
------------------
The migration is an administrative ClickHouse migration. It requires the
ClickHouse connection environment (`CLICKHOUSE_HOST`, `CLICKHOUSE_PORT`,
`CLICKHOUSE_DATABASE`, `CLICKHOUSE_USER`, and `CLICKHOUSE_PASSWORD` when used)
but does not require the Flask `SECRET_KEY`. The web application still requires
`SECRET_KEY`; this migration only removes the unnecessary administrative import
coupling.

The migration adds any missing identity columns, ensures
`idx_evidence_record_key`, preflights table state, fences `events_buffer`, and
then uses a bounded batched shadow-table rewrite only when work is required.
Missing and partial schemas are converged from ClickHouse metadata. After each
identity-column ADD the migration re-queries `system.columns`; after index ADD it
re-queries `system.data_skipping_indices`. It aborts before destructive rewrite
if required schema/index postconditions are not true.

Partial schema convergence includes data repair, not only DDL repair. If
`evidence_record_key` already contains valid v2 keys but
`evidence_identity_version` or `evidence_identity_quality` was added later, the
migration performs a shadow rewrite to repopulate the missing metadata while
preserving the existing valid v2 key.

The canonical index DDL is:
`ALTER TABLE events ADD INDEX IF NOT EXISTS idx_evidence_record_key evidence_record_key TYPE bloom_filter(0.01) GRANULARITY 4`

The invalid duplicate-keyword form
`ALTER TABLE events ADD INDEX IF NOT EXISTS INDEX idx_evidence_record_key ...`
must never be generated.

Handling:
- Missing keys are generated as v2.
- Existing `erk:v1:` keys are treated as obsolete Phase 0A identities and are
  upgraded to v2 during the dedicated migration.
- Existing valid v2 keys are preserved unless `--recompute-existing` is
  supplied.
- Unknown or malformed keys, including non-v2 prefixes and malformed
  `erk:v2:` values that do not match `erk:v2:<64 lowercase hex chars>`, are
  deterministically repaired to v2.
- Valid v2 keys with empty or invalid version/quality metadata keep their key
  and have metadata repopulated from retained evidence.
- `--recompute-existing` recalculates targeted rows from retained evidence and
  writes v2, covering missing, v1, malformed, and incorrect v2 keys.
- `--case-id` limits identity mutation to that case. The current migration still
  copies the full `events` table and reports this explicitly.
- A fully migrated v2 table performs status/preflight checks and exits without
  shadow creation, row streaming, table rename, or index materialization.
- `--dry-run` is read-only. It performs no DDL, no Buffer drains/fences, no
  inserts, no mutations, and no index creation or materialization.
- `--status` is read-only.

Python `--batch-size` controls only insert grouping into the shadow table. It is
not a ClickHouse source-query memory control. The default is `1000` rows and can
also be set with `EVIDENCE_IDENTITY_INSERT_BATCH_SIZE`. If an HTTP transport
timeout occurs while writing a shadow insert batch, the migration retries that
batch as smaller chunks before failing. Source reads use a migration client with
conservative defaults:
- `max_threads = 1`
- `max_block_size = 8192`
- `max_execution_time = 0`
- `send_receive_timeout = 86400`

`max_execution_time = 0` is passed as the ClickHouse query setting for the
migration client/source stream, which ClickHouse uses as no server-side
execution-time limit. The transport timeout is set separately to a large
explicit value so long forensic streams do not inherit the normal interactive
five-minute HTTP timeout. The migration does not globally alter ClickHouse
configuration, does not raise or disable global memory limits, and does not use
`LIMIT ... OFFSET` pagination.

Source rewrite design
---------------------
When a destructive rewrite is required, the migration enumerates case partitions
deterministically:

`SELECT DISTINCT case_id FROM events ORDER BY case_id`

It then streams each case separately:

`SELECT <insertable columns> FROM events WHERE case_id = {case_id:UInt32}`

There is no source row `ORDER BY`; identity generation is per-record and does
not depend on traversal order. Each case is further split into timestamp windows
before streaming, controlled by `--source-window-seconds` or
`EVIDENCE_IDENTITY_SOURCE_WINDOW_SECONDS` with a default of 900 seconds. Dense
timestamp buckets are recursively subdivided before streaming when their row
counts exceed `--source-window-max-rows` or
`EVIDENCE_IDENTITY_SOURCE_WINDOW_MAX_ROWS`, down to
`--source-window-min-seconds` or `EVIDENCE_IDENTITY_SOURCE_WINDOW_MIN_SECONDS`.
Large cases are still streamed through ClickHouse's row-stream API using the
migration source settings above. Memory is bounded by ClickHouse stream block
size plus the Python insert batch, not by the number of rows in a case. A
174,899,397-row case therefore does not require materializing 174,899,397 rows
in Python or keeping one HTTP stream open for the entire case.

The migration may copy multiple disjoint source windows concurrently with
`--copy-workers` or `EVIDENCE_IDENTITY_COPY_WORKERS`. This is still one
coordinated migration: one process owns the Redis lock, Buffer fencing, shadow
validation, source recount, and final swap. Copy workers run as child processes
so Python identity generation can use multiple CPU cores, and each child process
reuses one ClickHouse migration client across its assigned windows. Operators
must not run multiple independent migration commands in parallel.

Buffer safety
-------------
Operators must stop event-producing services first. The migration cannot prove
systemd state, so it also removes the writable Buffer target before the
authoritative source snapshot. The sequence is:

1. Acquire the destructive rewrite guard.
2. Verify `events_buffer` exists only as the expected Buffer-engine ingestion
   table.
3. Run `OPTIMIZE TABLE events_buffer` as a preliminary drain/diagnostic when
   supported by the current ClickHouse deployment. This can reduce or reveal
   pending rows, but it is not the authoritative forensic snapshot boundary.
4. Remove/fence the verified Buffer ingestion target.
5. Verify `events_buffer` no longer exists.
6. Count authoritative source rows in `events`.
7. Create and fill `events_evidence_identity_backfill`.
8. Validate `shadow_row_count == source_count_before_copy`.
9. Strictly validate Evidence Identity keys and metadata on the shadow table.
10. Recount original `events` and validate
   `source_count_before_swap == source_count_before_copy`.
11. Synchronously verify the Redis rewrite-lock token is still owned.
12. Rename `events` to `events_evidence_identity_previous` and the shadow table
   to `events`.
13. Recreate `events_buffer` against the final active table.

The forensic snapshot boundary is established after the verified Buffer
ingestion target has been removed, not by `OPTIMIZE TABLE` alone. If pending
Buffer rows cannot be proven zero, the migration fails closed before the shadow
rewrite. If `events_buffer` exists with an unexpected non-Buffer engine, the
migration aborts without dropping, detaching, recreating, or modifying it.

The destructive rewrite guard uses Redis directly from administrative
environment settings (`REDIS_HOST`, `REDIS_PORT`, `REDIS_DB`, and
`REDIS_PASSWORD` when used). It does not import Flask `Config` and does not
require `SECRET_KEY`. Destructive Evidence Identity rewrites require the Redis
lock, renew the lock lease while running, renew only when the stored token still
matches the holder, synchronously verify token ownership before swap, and
release only the matching token on exit.

Final validation
----------------
Before the shadow can be swapped into `events`, the migration enforces these
scoped postconditions on `events_evidence_identity_backfill`:
- `empty evidence_record_key rows = 0`
- `erk:v1 evidence_record_key rows = 0`
- `unknown/malformed evidence_record_key rows = 0`
- `invalid v2 identity metadata rows = 0`
- `valid erk:v2 rows = expected scoped row count`

With `--case-id`, these validation counts apply to the targeted case. Other
cases are still copied into the shadow unchanged. After a successful swap, the
same validation is repeated against active `events` as a post-swap sanity check.

Previous and shadow tables
--------------------------
`events_evidence_identity_previous` is a rollback table and is not silently
dropped. If it exists and a new rewrite is needed, the migration aborts by
default. Operators may rerun with `--replace-previous` only after validating,
archiving, or intentionally discarding that rollback copy.

`events_evidence_identity_backfill` is a disposable stale shadow from an
interrupted pre-swap run. If `events` is still active and
`events_evidence_identity_previous` is absent, the rerun discards the stale
shadow after preflight and creates a fresh shadow. This applies whether the
stale shadow has zero rows or millions of partial rows. Operators do not need to
manually clean up the shadow before rerunning.

Failure handling
----------------
If the Buffer cannot be safely fenced, no snapshot is taken and no shadow table
is created.

If the source row count changes during the copy, the migration does not rename
tables and leaves the original `events` table active.

If shadow validation fails, the migration does not rename tables and does not
recreate a writable Buffer target before a successful swap. The operator output
reports the active `events` table row count when safely obtainable, Buffer
state, shadow state and row count when safely obtainable, rollback table state,
whether the authoritative table was swapped, and the next recovery action.

If memory, timeout, connection loss, source-stream, insert, shadow-count, or
source-recount failures occur during the destructive stage, `events` remains
authoritative, `events_evidence_identity_previous` remains absent, the partial
shadow may remain for diagnostics, and `events_buffer` remains absent/fenced.
Operators should keep event-producing services stopped. The next rerun can
discard and rebuild the interrupted shadow.

If `events_evidence_identity_previous` already exists and a rewrite is required,
the migration aborts by default before fencing Buffer ingestion. Operators may
rerun with `--replace-previous` only after validating, archiving, or
intentionally discarding that rollback copy.

Rollback
--------
After a successful swap, keep `events_evidence_identity_previous` until
validation is complete. To roll back, stop services, drop/recreate
`events_buffer` around a rename that restores the previous table to `events`,
then recreate `events_buffer`.

Recommended operator flow
-------------------------
1. Stop event-producing CaseScope services:
   `sudo -n /usr/bin/systemctl stop casescope-web`
   `sudo -n /usr/bin/systemctl stop casescope-workers`
   Stop any separate scheduler/beat unit if the installation has one.

2. Back up ClickHouse.

3. Run the normal event schema migration:
   `cd /opt/casescope`
   `/opt/casescope/venv/bin/python migrations/add_events_table.py`

4. Check Evidence Identity status:
   `/opt/casescope/venv/bin/python migrations/add_evidence_record_identity.py --status`

5. Inspect row counts, v1/v2 distribution, previous/shadow table state, Buffer
   pending rows, and index state.

6. Dry-run:
   `/opt/casescope/venv/bin/python migrations/add_evidence_record_identity.py --dry-run`

   This performs no DDL or data writes.

7. Run the migration:
   `/opt/casescope/venv/bin/python migrations/add_evidence_record_identity.py --batch-size 10000`

   To intentionally recompute all targeted existing keys:
   `/opt/casescope/venv/bin/python migrations/add_evidence_record_identity.py --batch-size 10000 --recompute-existing`

8. Check status again:
   `/opt/casescope/venv/bin/python migrations/add_evidence_record_identity.py --status`

9. Verify row count unchanged, no unexplained empty keys, expected v2 count, no
   unintended v1 keys, Buffer recreated, and evidence index present.

10. Retain `events_evidence_identity_previous` until validation is complete.

11. Restart services:
   `sudo -n /usr/bin/systemctl start casescope-workers`
   `sudo -n /usr/bin/systemctl start casescope-web`

4.12.10 production hardening does not change Evidence Identity v2 semantics.
