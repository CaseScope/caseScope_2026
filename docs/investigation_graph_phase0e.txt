Phase 0E — Existing-Surface Integration + Support Lifecycle Expansion
=====================================================================

1. Purpose
----------
Make the Investigation Graph usable from existing CaseScope analyst surfaces
and complete current-source support lifecycle so edges cannot remain falsely
ACTIVE after their supporting evidence is removed.

2. Accepted baseline
--------------------
Version: 4.15.1
Commit:  7740eaea31c24a8006d6ac7b9a0326dd670d9ea7
Release: 4.16.3 corrective pass over 4.16.0/4.16.1/4.16.2

Phases 0A–0D remain ACCEPTED / LOCKED.

4. GraphPivotService contract
-----------------------------
File: utils/graph_pivots.py
API:  POST /api/graph/<case_uuid>/pivot
Body: { "kind": "...", "reference": { ... } }

Read-only. Never creates GraphEntity / GraphRelationship / GraphRelationshipEvidence.
Case-scoped via Case.get_by_uuid then server-side native object lookup.
Bounds: max 25 roots, 50 ERKs, 50 relationship IDs; truncated=true when capped.
VIEWER may call pivots.

5. Evidence -> graph reverse provenance
---------------------------------------
kind=evidence uses GraphEntityObservation.evidence_record_key and
GraphRelationshipEvidence.evidence_record_key (ACTIVE support only).
Does not reconstruct facts from event fields.

6. Process Hunting authoritative vs exploratory
-----------------------------------------------
Exploratory tree may use hostname+PID.
Authoritative PROCESS requires ERK, memory_process_id, or other accepted
execution anchor. PID-only never resolves as PROCESS; HOST may be offered.

7. Memory identity review
-------------------------
Within one MemoryJob, parser merges on (job_id, pid).
Preferred identity: MemoryProcess.id + job_id + pid + create_time (or native
support key as execution anchor). Memory processes never merge to event
processes by hostname+PID.

10. Network / DNS
-----------------
RESOLVED_TO NOT ENABLED — INSUFFICIENT SOURCE CONTRACT.
Reason: CaseScope currently retains query, answers, pcap_id and Zeek uid, but
not Zeek trans_id or another exact DNS transaction/source-record identity.
Zeek uid identifies the connection carrying DNS messages, not one DNS exchange,
so repeated identical query/answer activity could collapse support provenance.
Event PROCESS CONNECTED_TO remains DISABLED.
Upgrade reconciliation: migrations/invalidate_phase0e_4160_dns_relationships.py
transitions existing zeek_dns_resolved_to_ip support from 4.16.0 to INVALIDATED
and revalidates affected relationships so zero-current-support DNS edges become
UNSUPPORTED historical rows.
The reconciliation is restart-safe: reruns identify relationships from all
support rows produced by the withdrawn extractor, including already-INVALIDATED
support, and revalidate case-by-case.

11. Exact IOC provenance
------------------------
PostgreSQL table ioc_evidence_matches stores case_id, ioc_uuid, ioc_id,
evidence_record_key, matched_field/value, source_ref, support_state.
Written during tagging from known IOC object (exact uuid).
Retagging uses scan revalidation: previous ACTIVE exact matches become pending,
current matches are reproven, and unreproved rows become INVALIDATED. Exact
provenance scans fail explicitly on ClickHouse errors and malformed/non-v2 ERKs
are rejected rather than persisted.
events.ioc_types remains display-only and never proves which IOC matched.

12. KnownSystem / KnownUser
---------------------------
HOST = known_system:<KnownSystem.id> (never hostname search as authority).
USER prefers SID, then authority+username; bare username is ambiguous.

13. Typed finding pivots
------------------------
unified_finding pins case/analysis_id/source_system/dedup_key/finding_id and
must be loaded server-side before support ERKs are derived.
pattern_match pins case/pattern_match_id and loads the PostgreSQL row.
Client-supplied ERKs are never accepted as proof for an invented finding.
Findings seed pivots; they do not author graph edges.

14–18. Support lifecycle
------------------------
Service: utils/graph_support_lifecycle.py
Support states: ACTIVE, PENDING_REMOVAL, PENDING_REVALIDATION, UNAVAILABLE, INVALIDATED
Relationship states: ACTIVE, UNSUPPORTED, INVALIDATED
support_count / active_support_count = ACTIVE supports only
source_ref_type/id: CASE_FILE | PCAP_FILE | MEMORY_JOB

Removal sequence:
1) stream ERKs / mark PENDING_REMOVAL
2) if lifecycle preparation fails, abort before evidence deletion
3) delete ClickHouse/PG/native source
4) finalize deleted sources UNAVAILABLE + revalidate relationships
5) on partial failure, restore ACTIVE only for failing/untouched sources whose
   evidence still remains; already-deleted sources are never restored ACTIVE.

Reprocess sequence:
1) PENDING_REVALIDATION / INVALIDATED for old generation
2) re-ingest + rematerialize
3) equivalent support reactivates same canonical edge (extractor version on provenance)

PCAP_FILE and MEMORY_JOB native source deletion/reprocessing paths are routed
through the same lifecycle boundary as CaseFile event support. PCAP reindex is
also wrapped in begin/finalize/restore revalidation. Successful memory ingestion
materializes Phase 0E memory graph relationships immediately for that MemoryJob.
Failed CaseFile deletion/revalidation restores both GraphRelationshipEvidence
and exact IOCEvidenceMatch support when source evidence remains.
CaseFile ERK fallback support is processed in batches. Source-ref-less
IOCEvidenceMatch rows discovered through the exact CaseFile ERK set are
backfilled with CASE_FILE + case_file_id before becoming pending, so later
restore/finalize operations are symmetric.

19. Failure / recovery
----------------------
PENDING states hide support from active counts before destructive ops.
Crash-safe preference: falsely non-active over falsely ACTIVE.

20–21. Threads / Saved Views
----------------------------
Frozen Thread snapshots and snapshot_sha256 are never rewritten.
live_source_available updates separately via live ERK lookup.
Saved View stable relationship refs preserved; unsupported edges warned in UI.

22. New entity / relationship contracts
---------------------------------------
No IOC/Finding graph node types added.
New relationship types: RESOLVED_TO, LOADED_MODULE, SERVICE_RUNS_PROCESS,
SERVICE_RUNS_IMAGE, SERVICE_RAN_AS, HAS_SECURITY_CONTEXT (last two event
variants not enabled).

23. Anti-inference
------------------
No AI/narrative extractors.
No PID-only PROCESS / CONNECTED_TO from events.
No username-only USER merge.
No source_host as network owner.
No raw_json path scraping for REFERENCES.

24. Permissions
---------------
Pivots: read-only, VIEWER allowed.
Thread/Saved View mutation: write access unchanged.
Source removal: existing admin/write gates.

25. Scale limits
----------------
Pivot bounds 25/50/50.
ERK streaming / batched support updates (DEFAULT_BATCH_SIZE=500).
IOC match streaming LIMIT/OFFSET.
Memory process resolution is lazy per PID (two-row ambiguity check). Memory
artifact extraction uses bounded id-keyset pages so commits do not run while a
PostgreSQL streaming cursor remains open.
Successful memory ingestion remains a successful MemoryJob even if graph
projection is incomplete; graph materialization reports success/errors
separately in the task result.

26. Known limitations
---------------------
Memory module top-level UI pivot absent.
DNS RESOLVED_TO NOT ENABLED — missing exact DNS transaction identity.
Event service/registry/scheduled-task extractors NOT ENABLED — insufficient source contract.
WAIVER-0C-001 may still apply to baseline IOC queue regression if unchanged.

27. Phase 0F boundary
---------------------
No temporal context services, report snapshots, graph image capture, or AI
summarization over frozen report context.
